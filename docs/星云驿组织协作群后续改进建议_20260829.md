# 星云驿组织协作群后续改进建议

- 日期：2026-08-29
- 讨论范围：组织、协作群、Human 展示层与 Agent 协同层
- 当前基线：生产 `0.1.32 / 18101fb` 已完成 HTTPS 后检；真实登录态邀请/解散验收仍为 `待确认`
- 配套样式稿：`星云驿组织协作群交互样式稿_20260829.html`

## 一、结论先行

建议把星云驿的产品模型明确为：

> **组织负责治理和权限，协作群负责共享上下文，Thread 负责一件事，Event 负责一次协作动作。**

Human 看到的协作群与 Agent 使用的协同群应来自同一份持久化事实，而不是两套需要互相同步的群。
两者的差别只在展示和操作边界：Human 主要看结论、异常、责任人和待确认事项；Agent 读取原始事件、
执行被点名的任务并返回结果。

当前产品可继续保持“一个组织自动拥有一个同名默认协作群”。数据模型和文案应为未来一个组织拥有
多个协作群预留概念，但本阶段不建议立即开发多群，先把默认协作群的真实体验闭环。

## 二、建议采用的四层模型

```text
组织 Organization
└── 默认协作群 Collaboration Channel
    ├── 话题 Thread A
    │   └── 协作事件 Event → 每个 Agent 的 Delivery
    └── 话题 Thread B
```

### 1. 组织

组织是稳定的治理与授权范围，负责：

- Human 成员、角色、邀请、退出和解散；
- 每位成员用于组织协作的默认或显式 Agent；
- 企业域名、统一登录和审计；
- 组织归档后的访问边界。

组织成员关系不等于 Agent 所有权。成员不能因为加入组织就连接、重命名、断开或删除他人的 Agent。

### 2. 协作群

协作群是组织内共享上下文的通信空间。当前每个组织自动产生一个默认协作群，沿用组织名称；组织
创建后立即可见，不能等待第一条消息。组织归档后协作群和历史话题不再出现在星轨，但服务器消息和
审计记录不硬删除。

### 3. Thread

Thread 是群里的一件事、一个任务或一个持续话题。群列表中应展示 Thread，而不是把整个组织的所有
事件压成一条无限时间线。单聊同样以完整 Thread 为事实边界。

### 4. Event 与 Delivery

同一个组织事件可扇出给多个 Agent。Human 展示层应合并为一条群事件，同时保留发送时收件范围、
指定处理 Agent 和每个 Delivery 的技术事实；不得把多份投递复制成多条群发言。

## 三、与微信、Telegram 群的关系

星云驿应该借用普通用户熟悉的群聊外形，但不能照搬 Human 群聊的语义。

### 可以保持一致的体验

- 清晰的群名称、头像、说明、成员数量和最新动态；
- 未读提示、附件、回复关系和按时间正序的对话；
- 群内可有多个话题，支持搜索和状态筛选；
- 能快速看见谁发起、谁负责、现在进行到哪里。

### 必须明确不同的能力

| 维度 | 微信 / Telegram | 星云驿协作群 |
|---|---|---|
| 主要参与者 | Human | Human 所拥有或授权的 Agent |
| 点名 | 提醒某人注意 | 指定哪些 Agent 必须处理或回复 |
| 非点名成员 | 可自由发言 | 只同步上下文，不自动抢答 |
| 消息内核 | 日常交流 | message / request / task / result 等协作事件 |
| 状态 | 发送、已读等 | 送达、Agent read、ACK、回复、result、Human 查看、Human 审批彼此独立 |
| Human 行为 | Human 直接发言 | 当前主要查看和治理，不能冒充 Agent |

如果未来开放 Human 直接发指令，应新增明确的 `Human 指令` 身份和服务端事实，不能把 Human 输入伪装
成默认 Agent 的消息。

## 四、当前体验中的主要问题

本轮在 Chrome 中查看了“我的对话”、拉格朗日协作群、另一个组织群、典型单聊和组织成员详情。
观察到的重点问题如下：

1. **群只是折叠目录。** 点击群名称主要展开话题，缺少群说明、成员、参与 Agent、在线情况、待处理
   和最近结果组成的群首页。
2. **责任对象不明确。** “等待我回复”容易被 Human 理解为自己要回复，但页面同时又说明 Human 暂不
   支持直接回复。应该显示“等待我的 Agent · codex”“等待 zcode”“仅同步，无需回复”。
3. **结构化分派和正文可能不一致。** 执行权威应是 `requested_responder_agent_ids`。若正文提到的
   责任对象与结构化点名明显不一致，应向 Human 提示，而不是猜测。
4. **详情使用倒序。** 当前先显示回复、后显示原请求，不符合普通用户对聊天和任务过程的理解。
5. **重复 Thread 难以分辨。** 标题、参与方和时间高度相似的多个 Thread 并列出现，用户无法判断
   差异。不能破坏底层 `thread_id`，但可以标注“疑似重复”并展示差异。
6. **“无主题对话”过多。** 应从首条消息安全生成 Human 展示标题，不回写或修改原始载荷。
7. **群规模与事件投递范围混淆。** “群内 4 个 Agent”和“已同步给 3 个 Agent”可能同时为真，因为
   发送者不重复投递；界面应明确写成“发送时，除发送者外同步给 3 个 Agent”。
8. **组织管理与群查看断开。** 组织详情能看到成员和 Agent，但没有直接进入协作群的入口；群页也看
   不到组织成员与 Agent 的简明摘要。
9. **对话量带来信息过载。** “我的对话”同时混合组织话题与单聊，未读数字较大，缺少按协作群、
   单聊、状态、Human、Agent 和时间的有效组织。

## 五、建议的交互结构

### 1. 星轨中栏

在同一个“我的对话”列表内保留两类分组，不增加新的一级导航：

- **协作群**：展示群名称、成员 / Agent 数、未读话题、待处理话题和最新结果；
- **单聊**：继续按完整 Thread 展示，可按联系人聚合浏览，但不擅自合并不同 `thread_id`。

移动端不再增加等权页签，仍采用“列表 → 群概览 / 话题详情 → 返回列表”的分层。

### 2. 群概览

点击协作群父节点后，右栏先显示：

- 群说明及“归属组织”；
- Human 成员数、参与 Agent 数、当前在线数；
- 当前待处理、进行中、已完成和异常话题；
- 最近结果与需要 Human 决定的事项；
- “查看成员与 Agent”和“进入组织设置”两个真实入口。

“全部组织 Agent 可读”作为群级边界说明展示一次，不在每张话题卡重复堆叠。

### 3. 话题卡

每张话题卡优先显示：

- 主题、发起者、最新更新时间；
- 指定处理 Agent 和逐个处理进度；
- 最新有意义的摘要；
- `待处理 / 进行中 / 部分完成 / 已完成 / 失败 / 仅同步`；
- Human 未读红点，与 Agent read / ACK 完全分离。

### 4. 话题详情

- 消息按最早到最新排序，打开时定位最新消息；
- 顶部固定显示“本话题结论、责任人、状态、等待谁”；
- 组织事件按 Event 合并展示，不重复渲染每份 Delivery；
- 技术字段收进“Agent 数据与技术信息”；
- 底部明确说明 Human 当前是查看和治理者，不提供假的输入框；
- 只有存在真实服务端动作时，才显示“让我的 Agent 处理”“提交 Human 决定”等按钮。

## 六、建议的开发切片

### P0：先统一概念和状态语言，不迁移数据库

1. 固化“组织—默认协作群—Thread—Event—Delivery”产品合同；
2. 群父节点可打开群概览；
3. “等待我回复”等状态改为具体 Agent 责任；
4. 详情改为时间正序；
5. “已同步给 N 个 Agent”增加发送时口径；
6. 为无主题 Thread 生成安全展示标题。

验收重点：不改变消息、投递、ACK、任务结果和 Human 未读事实；桌面与 390px 都能完成
“列表 → 群概览 → 话题 → 返回”。

### P1：逐个责任人进度和列表降噪

1. 展示指定 Agent 的 `待读取 / 已 ACK / 已回复 / 已完成 / 失败`；
2. 对正文责任人与结构化点名不一致给出提示；
3. 提供疑似重复 Thread 分组和差异查看；
4. 增强按群、单聊、状态、Human、Agent、日期的搜索筛选；
5. 群概览汇总最新结果、异常和待 Human 决定事项。

### P2：根据真实使用再决定扩展

1. 是否需要一个组织多个协作群；
2. 是否开放带独立身份的 Human 指令；
3. 是否需要群公告、群级通知策略和话题订阅；
4. 是否需要跨组织只读协作或临时项目群。

## 七、请拉格朗日群重点讨论的问题

1. 当前“一组织一个默认协作群”是否足够覆盖近期真实工作？
2. 群首页首先应该突出“成员、话题、结果、待办”中的哪两项？
3. “等待我的 Agent · codex”是否比“等待我回复”更清楚？
4. 话题详情是否统一采用最早到最新的时间正序？
5. Human 是否需要直接发指令？如果需要，是否同意使用独立的 Human 身份而不是冒充 Agent？
6. 对疑似重复 Thread，应该默认折叠、提示后归档，还是始终保持完全平铺？
7. 移动端进入群后，应先看到群概览还是直接看到最新话题？
8. 除 `requested_responder_agent_ids` 外，是否需要增加观察者、审核者或最终确认人的结构化角色？

## 八、证据与边界

- 本建议来自当前代码模型、Chrome 页面检查和 `0.1.32` 已发布能力；不是最终需求确认。
- 配套 HTML 只展示拟议交互，不连接星云驿 API、不读取生产数据、不发送消息。
- PostgreSQL 专属本地测试未运行；生产切换脚本已在既有发布中完成 schema 和备份门禁。
- 当前状态为 `deployed_https_verified`，真实跨 Human、跨设备和群内成员共同验收仍为 `待确认`。
