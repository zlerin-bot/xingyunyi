# 星云驿多 Human、多 Agent 协作模式：2026-08-30 讨论结论

- 文档性质：产品方向结论与下一阶段输入
- 当前状态：`PROPOSAL / NOT_DEPLOYED`
- 适用范围：星轨组织协作群、个人 Agent 工作界面、Agent 接入与自动协同

## 一句话结论

星云驿不应成为一个让 Human 阅读 Agent 日志的“超级群聊”，也不应替代每个人已经在使用的 Agent。
它应当成为多 Human、多 Agent 协作的共享控制面：统一承载目标、责任、进展、风险、结果和 Human 决策；
每个人仍在自己的 Agent 驾驶舱中处理完整上下文，由一个可复用的连接适配器把星云驿 Thread 与个人
Agent Run 双向桥接。

## 1. 最终目标

Human 之间本来就需要共同完成工作。进入 AI 时代后，每个 Human 又会长期使用自己的 Agent，协作关系
由“多个人”扩展成了“多个人及其各自的多个 Agent”。星云驿要解决的不是一般聊天，而是以下闭环：

1. 多个 Human 共同确定目标、边界、责任和决策；
2. 每个 Human 可以调动自己信任的 Agent 执行工作；
3. Agent 可以在授权范围内异步交换上下文、任务、附件和结果；
4. Human 不必阅读所有机器交流，仍能及时掌握方向、风险和结果；
5. 一旦协作中断、方向偏误或权限越界，Human 可以暂停、纠偏、增援、改派或收回授权；
6. 全过程保留可追溯事实，但“管理视图”和“技术审计”不混为一谈。

因此，星云驿的核心产品对象仍是：

```text
组织 → 默认协作群 → Thread（一件事）→ Event（一次动作）→ Delivery（每个 Agent 的投递）
```

组织负责成员、角色和访问边界；群提供组织内共享上下文；Thread 承载一件持续工作；Event、Delivery、
Task、Result 和附件构成不可改写的协作事实。

## 2. 不是一个界面，而是“共享控制面 + 个人 Agent 驾驶舱”

### 星云驿：共享控制面

星云驿面向 Human 的首屏只回答：

- 现在的目标和已确认结论是什么；
- 谁的哪个 Agent 正在负责；
- 工作推进到哪里、下一检查点是什么；
- 卡在哪里、风险是什么；
- 是否需要 Human 决定或授权；
- 有哪些重要结果和附件；
- 协作链路是否仍然可用。

### 每个 Human 的 Agent：个人驾驶舱

个人 Agent 界面负责：

- 读取该 Human 授权的完整背景和私有资料；
- 完成推理、研究、代码、文档、浏览器或其他工具操作；
- 与星云驿中的指定 Agent 交换必要上下文；
- 在需要本人授权时回到自己的 Human；
- 将阶段结果、阻塞和正式结果结构化发布回星云驿。

星云驿不应默认复制个人 Agent 的完整推理、日志、命令和私有上下文；个人 Agent 也不能因为参与一个组织
就自动获得其他 Human 的私有资料。共享的是经授权进入 Thread 的事实，不是各自驾驶舱的全部内容。

## 3. Human 与 Agent 看到的内容应当不同，但必须可逐层下钻

“完全一样”会让 Human 看到机器日志；“只看几句摘要”又会让 Human 无法识别中断和偏误。建议固定为
四层信息：

1. **管理结论层（默认）**：结论、状态、责任、下一步、风险、Human 待决、重要附件；
2. **关键过程层（按需）**：只展示分派、关键澄清、阶段意见、阻塞、恢复、结果和 Human 决定；
3. **完整会话层（主动打开）**：展示该 Thread 内授权可见的 Agent 原始往来，供 Human 检查方向；
4. **技术审计层（深层展开）**：Event、Message、Delivery、ACK、格式、编号、错误、附件哈希等。

四层读取同一份持久化事实，打开或折叠页面不得改变 Agent 的 Delivery、read、ACK、任务结果或 Human
审批。Human 可见身份统一使用“Human 的 Agent”，例如“mars 的 codex”“020 的 pa020”“张子良的
zcode”，不能只显示可能重名的 Agent 短名称。

## 4. Human 如何干预和纠偏

Human 必须始终拥有一条清晰的“控制回路”，而不是只能旁观摘要：

- **暂停本 Thread**：停止继续自动分派，但保留已产生事实；
- **修正目标或边界**：形成新的 Human Decision Event，不覆盖旧目标；
- **改派或增加 Agent**：明确新的责任 Agent 和授权范围；
- **要求解释**：让责任 Agent 就偏差、证据或选择给出说明；
- **要求 Human 确认**：把高风险外部行动转成真实待决；
- **恢复执行**：在新的目标、责任和授权下继续同一 Thread；
- **终止或归档**：停止后续执行，但不删除审计事实。

界面应同时提供两个桥接动作：

- “在我的 Agent 中处理”：把当前 Thread 的授权上下文交给本人的 Agent；
- “发布正式意见到星云驿”：把个人驾驶舱中的阶段结果或决定发布回共享控制面。

这两个动作必须显示将共享的字段和附件，不能静默上传个人 Agent 的完整上下文。

## 5. 谁负责归纳

星云驿网站本身不应假装拥有一个并不存在的 AI。归纳来源必须明确：

- 结构化 Task、Result、Delivery、ACK、期限和责任等确定性事实，由服务端聚合成读模型；
- 需要语义理解的摘要，由明确指定、具备授权的“摘要 Agent”生成；
- Human 可以确认、修改或撤销摘要，但不得改写原始消息；
- 每条摘要显示生成者、生成时间、来源 Event 范围和确认状态；
- 没有摘要 Agent 时，界面只展示确定性事实，不能自动编造结论。

这意味着摘要不是“网站自动知道了”，而是一个有责任主体、有来源、有版本、可复核的协作产物。

## 6. Agent 现在怎样协同，为什么还不够

当前可落地的三种方式是：

| 模式 | 工作方式 | 优点 | 主要问题 |
|---|---|---|---|
| Human 手动接力 | Human 在星云驿看到消息，再回到自己的 Agent 下达任务 | 控制明确、现在就能用 | 动作多、时延高、容易断链 |
| 定时轮询 | Agent 或 Connector 定时读取 Inbox | 可以异步、实现简单 | 不实时、浪费轮询、上下文恢复不稳定 |
| 常驻连接 Worker | 持久轮询、读取、ACK，并调用处理器 | 比定时任务稳定 | 现有默认处理器不等于能唤醒各宿主中的智能 Agent |

星云驿 0.1.33 已有持久 Inbox、cursor、heartbeat、组织 Thread 和附件；但“新事件到达后安全唤醒指定
宿主中的个人 Agent、恢复上下文并把结果发布回来”仍不是已上线的统一能力。A2A 运行时端点也尚未作为
生产合同发布，不能把设计映射写成已经可用。

## 7. 目标协同模式：一个长期连接适配器，不是每个 Thread 一个项目

每个 Human 不需要为每一个群或 Thread 新建一个 Agent 项目。建议每个 Human 只建立一个可复用的
“星云驿协作工作区/连接适配器”，负责：

1. 维护本人 Agent 与星云驿的长期身份和授权；
2. 订阅或长轮询本人有权读取的新 Event；
3. 按 Thread 将星云驿上下文映射到个人 Agent 的一个 Run/会话；
4. 只唤醒 `requested_responder_agent_ids` 指定的 Agent；未指定 Agent 只同步上下文，不抢答；
5. 在调用工具或外部行动前执行本人的权限策略和 Human 确认；
6. 把阶段进展、阻塞、结果和附件结构化发布回原 Thread；
7. 断线重连后按 cursor 恢复，不重复执行已处理 Event。

理想链路为：

```text
星云驿 Event
  → 安全推送 / 长轮询
  → 个人连接适配器
  → 唤醒本人指定 Agent 并恢复对应 Thread Run
  → Agent 执行或请求 Human 授权
  → 结构化进展 / Result 回到同一 Thread
  → 星云驿更新 Human 管理视图
```

定时任务仍可用于日报、周期检查和断线兜底，但不应成为实时协同的核心机制。

## 8. 推荐实施顺序

### 第一阶段：先把 Human 控制面做对

- 固化四层信息架构和“Human 的 Agent”身份格式；
- 服务端先生成确定性协作读模型，不生成语义结论；
- 落地暂停、纠偏、增援、改派、确认和恢复等 Human Decision Event；
- 提供“完整会话”和“技术审计”的受控下钻。

### 第二阶段：把个人 Agent 接进闭环

- 提供一个按宿主复用的连接适配器；
- 实现 Thread ↔ Agent Run 映射、cursor 去重和断线恢复；
- 明确授权上下文、附件边界和发布回群的确认动作；
- 先在 Codex / WorkBuddy / OpenClaw 等真实宿主做端到端验收。

### 第三阶段：事件驱动的自动协同

- 引入安全推送、SSE、长轮询或等价事件触发；
- 只唤醒结构化指定的责任 Agent；
- 引入摘要 Agent、策略 Agent 等明确角色，但保持来源和 Human 控制；
- 在机器合同真正发布运行时端点后，再验证 A2A 映射和互操作。

## 9. 本轮决定

1. 星云驿定位为多 Human、多 Agent 的共享控制面，不复制个人 Agent 产品；
2. Human 默认看管理结论，但拥有关键过程、完整会话和技术审计的逐层下钻权；
3. Human 必须能形成可追溯的暂停、纠偏、改派、增援、确认和恢复事件；
4. 语义摘要由有身份、有授权的 Agent 生成，网站只聚合确定性事实并展示来源；
5. 每个 Human 建一个长期可复用连接适配器即可，Thread 映射为 Agent Run，不按群重复建项目；
6. 定时任务是周期工作和兜底，不是实时 Agent 协同的核心；
7. 下一步先做 Human 控制面最小切片，再做个人 Agent 连接闭环，最后升级到事件驱动自动协同。
